# RAG 三代范式对比

> [[RAG]] 从 2020 提出至今的三代演进。结构来自 [[RAG综述2023]]。

## 一句话区分

| 范式 | 核心特征 |
|---|---|
| **Naive RAG** | 索引 → 检索 → 生成，三段式固定流程 |
| **Advanced RAG** | 在检索**前后**插入优化环节 |
| **Modular RAG** | 打破链式结构，重构为**可插拔组件网络** |

## 关键差异

| 维度 | Naive | Advanced | Modular |
|---|---|---|---|
| 流程形状 | 固定链式 | 链式 + 前后处理 | 可自由插拔的网络 |
| 检索时机 | 单次，生成前 | 单次，生成前 | 迭代 / 递归 / 自适应 |
| 查询加工 | 无 | 重写、多查询扩展、HyDE | 同左 + 路由 |
| 索引优化 | 无 | 粒度、结构、元数据、对齐、混合 | 同左 + 记忆模块 |
| 新增模块 | — | — | 路由、记忆、预测 |
| 解决的核心问题 | 能跑通 | 检索质量与上下文质量 | 灵活性与知识缺口自补 |

## Naive RAG 的具体缺陷

来自 [[2023-gao-rag-survey]]：

-检索**精度低**——选中的文本块与问题错位
- 检索**召回率低**——遗漏相关文本块
- 可能喂入**过期信息**（恰是 RAG 本该先解决的）
- 增强环节引入**冗余与重复**
- 多段落时排序与风格/语气难协调
- 半结构化数据（如含表格的 PDF）被传统切分破坏完整性，输出连贯性受损

## Advanced RAG 的两处插入点

**预检索**（提升输入端质量）：
增强数据粒度、优化索引结构、添加元数据、对齐优化、混合检索。
查询侧：查询重写、多查询扩展、[[查询改写与HyDE]]。
技术细节：滑动窗口、细粒度分割（以命题为检索单元）、Small2Big。

**后检索**（提升输出端质量）：
[[重排序]]（把最相关挪到边缘，规避[[中间遗忘]]）、小模型过滤/压缩无关 token。

后检索之所以是**必需**而非可选，源于一个实证事实
（[[2023-liu-lost-in-the-middle]]）：改变答案文档在上下文中的位置，
准确率呈 U 型曲线——GPT-3.5-Turbo 位置 0 为 75.8%，位置 9 跌至 53.8%，
而 53.8% **低于闭卷基线 56.1%**。

**这意味着「检索到了但放在中间」可能比「没检索」更糟。**
重排的真正目的不是让顺序好看，而是把文档放到模型能看见的位置。
且U 型曲线不对称，尾部比中部高约 10 个百分点，故应**把最相关的放末尾**。

另一约束是[[阅读器饱和]]：阅读器性能在检索器召回率之前已饱和，
加更多文档只增加成本不提升准确率。这给 top-k 设定了收益递减的上界。

## Modular RAG 的三种增强过程

- **迭代检索**——检索与生成交替进行
- **递归检索**——用思维链拆解子问题，逐步细化搜索
- **自适应检索**——如 FLARE、Self-RAG，模型通过监控生成概率或生成「反思令牌」
  自主决定是否检索、何时停止

## 共同点

三代都建立在同一基础之上：参数化 seq2seq + 非参数化稠密向量索引 +
预训练神经检索器（[[2020-lewis-rag-original]]）。演进的是**工程成熟度**，
不是基本架构。

## 何时用哪个

- **Naive** —— 快速验证、成本敏感、语料简单
- **Advanced** —— 多数生产场景的默认起点；检索质量是主要瓶颈时优先加预检索
- **Modular** —— 需要跨数据源路由、知识缺口自补、多跳推理时
