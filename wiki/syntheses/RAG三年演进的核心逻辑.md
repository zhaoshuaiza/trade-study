# 综合理解：RAG 三年演进的核心逻辑

> 跨两份来源交叉得出的结论，非单篇复述。

## 综合结论

**RAG 的演进主线不是「检索算法变强」，而是「上下文质量控制权从检索器转移到生成流程」。**

2020 年的 RAG 把检索当作一个固定的前置步骤——检索一次，生成一次，顺序不可变。
2023 年的Advanced RAG 承认检索结果本身可能是有害的（噪声、冗余、错位），
于是在检索前后都插入加工。Modular RAG 更进一步，承认**「什么时候该检索」本身
应该是模型的决策**——Self-RAG 生成反思令牌自主触发检索，即是这个逻辑的终点。

换言之，2020 问「检索什么」，2023 问「检索来的东西怎么用、什么时候该用」。

## 各来源立场对比

| 来源 | 立场 | 依据 |
|---|---|---|
| [[2020-lewis-rag-original]] | RAG 是可微分记忆访问机制，重点在**训练**（端到端联合微调） | 论文核心贡献是训练配方 |
| [[2023-gao-rag-survey]] | RAG 是工程系统，重点在**流程编排**（三代范式） | 综述按组件与范式组织 |

两者不矛盾，而是**同一技术栈的不同层次**：2020 解决「能不能训」，2023 解决
「上线后好不好用」。

## 共识

1. 外部非参数化记忆的价值主要在**知识更新**与**可溯源**，而不仅是准确率
2. 检索质量是RAG 效果的上限——检不到就没用
3. 上下文位置影响信息利用率（[[中间遗忘]]）
4. RAG 与微调、提示工程互补

## 分歧 /张力

- **[[观点-RAG不彻底解决幻觉]]**：RAG 降低幻觉但引入新失效模式（过期事实、复读机）。
  而 2020 论文的乐观表述（「更符合事实」）与之存在张力——
  后者是实验报告，前者是机制分析，视角不同。
- **「更具体、更多样」的评价标准模糊**：2020 论文的生成质量结论缺乏量化指标，
  而2023 综述已转向precision/recall/归因质量等可测量指标。
  三年的评价体系明显 evolved。

## 尚未解决的问题

- RAG 与**长上下文窗口扩展**的边界：上下文能开到几十万 token 时，RAG 的独特价值还剩多少？
  [[2023-liu-lost-in-the-middle]] 给出了**部分反向证据**——扩大窗口不改善位置鲁棒性，
  因此长上下文无法替代 RAG 的「筛选 + 排序」职能。
  **但该文被测模型为2023 年的 GPT-3.5-Turbo / Claude-1.3，已过时**，
  2024-2025 模型的位置敏感性是否有改善仍待验证。
- **Agentic RAG**（检索作为 Agent 的工具而非固定前置步骤）在 2023-12 之后才成型，
  超出[[RAG综述2023]] 覆盖范围。
- [[中间遗忘]] 的**机制性解释**（位置注意力偏置）尚未摄入——
  [[2023-liu-lost-in-the-middle]] 只做了现象诊断，未提出架构修复方案。
- [[LostInTheMiddle2023]] 自身的重要限定：**阅读器性能早于检索器召回饱和**
  （见[[阅读器饱和]]）。这意味着「多召回」在多数场景下是浪费，
  但该结论未在更多任务域上验证。

## 三份资料合起来揭示的第四层问题

三份资料（2020原始论文、2023综述、2023实证）叠加后，浮现出一个
**前三份单独都看不到**的问题：

> RAG 的所有检索侧优化，最终都在解决**同一个约束**——
> 模型对上下文位置敏感且不可靠（[[中间遗忘]]）。

- 重排序要解决它 → 把相关内容挪到边缘
- 压缩/过滤要解决它 → 减少污染中间段落的噪声
- 限制上下文长度要解决它 → 缩短U 型曲线的危险区
- 查询感知上下文化要解决它 → 把查询同时放两端
- 锚定提示要解决它 → 给解码器一个「先提取再回答」的信号

**这解释了为什么 Advanced RAG 的手段看起来零散却方向一致。**
它们不是独立的技巧集合，而是对同一个底层约束的不同角度攻击。

同时，「扩大窗口不解决问题」这一发现给上述整套优化**提供了长期有效性依据**：
既然窗口变大也救不了位置敏感性，这些工程手段在上下文窗口持续增长的未来
**不会过时**。

## 与本知识库自身的关系

有意思的是，本知识库采用的 [[LLM Wiki]] 架构与 RAG 是**互补而非竞争**关系：

- RAG 是**运行时**召回——查询时刻定位片段
- LLM Wiki 是**编译时**产物——构建阶段把材料固化为完整语义单元

当页面量达到几百篇时，纯`index.md` 渐进加载的效率会下降，
那时才需要引入 BM25 + 向量重排，即RAG 手段。
**先编译，后检索，两者分处不同阶段。**

而本页揭示的「第四层问题」恰好说明：LLM Wiki 的**渐进式披露**
（`hot.md` → `index.md` → 具体页面）本质上就是把每次查询的上下文
**控制在较小规模**——从架构上规避[[中间遗忘]]，
而不是等出问题了再靠重排去补救。
