# 综合：RAG 与长上下文的分工

> 四份资料（2020 原始论文、2023 综述、2023 实证、2025 实证）交叉得出的结论。

## 综合结论

**RAG 与长上下文不是替代关系，而是分工关系。**

- **长上下文**负责「装得下」——把更多内容放进窗口
- **RAG** 负责「挑得准+ 放对位置」——只给真正需要的，且放在模型能看见的地方

四份资料各自提供了一个支撑点：

| 资料 | 支撑 |
|---|---|
| [[2020-lewis-rag-original]] | RAG 组合参数化与非参数化记忆，扩展窗口不改变知识更新成本 |
| [[2023-gao-rag-survey]] | Advanced RAG 的所有手段都在优化上下文质量 |
| [[2023-liu-lost-in-the-middle]] | 位置效应真实存在，中间位置**低于闭卷基线** |
| [[2025-long-context-evidence]] | **窗口变大不解决问题**；300 token 相关片段优于 113K 完整对话 |

## 核心论证

如果长上下文足够好，RAG 的价值就只剩「省token」——这是弱动机。

但 2024-2025 的证据显示，**长上下文是「装得下」而非「用得好」**：

1. **有效长度远小于宣称长度**（[[宣称长度与有效长度]]）
   —— LWM 宣称 1M、有效不足 4K
2. **中间位置会退化**（[[中间遗忘]]）
   —— GPT-3.5-Turbo 中间位置 53.8% <闭卷基线 56.1%
3. **长度本身即成本**（[[上下文腐蚀]]）
   —— 纯长度造成约 7.9% 损失，与干扰项无关

因此**「把所有材料塞进去让模型自己找」这条路走不通**。
必须有人（或规则）负责筛选与排序——这正是 RAG 的职能。

## 最直接的单一证据

Context Rot 的 LongMemEval 对照：

> 给出**约 113K token 的完整对话历史**，表现不如
> **只给约 300 token 的相关片段**。

差距是**两个数量级的上下文，输给了百分之一的上下文**。
这不是边际优化，这是**方向性差异**。

## 一个反直觉的推论

**整理得有条理反而可能有害。**

Context Rot 在**全部 18 个模型**上发现：随机打乱的 haystack
检索表现**优于**逻辑连贯的 haystack。作者解释——
连贯结构创造了更貌似相关的干扰项。

这对 RAG 有直接影响：把召回的段落**按时间或逻辑顺序重排**，
可能不如保持检索器给出的相关性顺序。

**这与 [[重排序]] 的实践建议形成张力**——
后者建议按相关性排序。两者并不矛盾（相关性排序 ≠逻辑连贯排序），
但值得注意：**排序的目标是让模型看清，不是让人类读懂。**

## 不构成 RAG 优势的场景

必须诚实标注反面证据：

**LongBench v2**（清华，2024-12）在真实长文本任务上，
人类专家在 15 分钟限制下也仅达 **53.7%**。
说明真实长上下文任务本身极难，部分困难源于任务而非模型。

另外，**长上下文在某些维度确实占优**：
一套横跨 12 个数据集的对比显示，长上下文模型正确率 56.3% vs RAG 的 49.0%——
**长上下文赢了总量**。但 RAG 在对话类与通用问答上有优势，
且在语料超出可用窗口、语料更新快于重训速度、
或需引用具体出处时是唯一选择。

**结论：不是「RAG 更好」或「长上下文更好」，而是「按需选择」。**

## 实践边界

| 场景 | 倾向 |
|---|---|
| 语料超出可用窗口 | RAG（长上下文装不下） |
| 需引用具体出处 | RAG |
| 语料更新快于重训 | RAG（重建索引比重训便宜） |
| 单文档深度推理 | 长上下文（避免切分破坏完整性） |
| 语料小且固定 | 长上下文（省去检索复杂度） |
| 对抗性/干扰项多 | RAG + 严格筛选（见[[阅读器饱和]]） |
